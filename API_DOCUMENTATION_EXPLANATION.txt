1. WHAT IS AN API?
==================

API means Application Programming Interface.

In this project, API means backend URLs that the frontend or another tool can call to perform actions.

Examples from this project:

POST /api/auth/login/
GET  /api/employees/
POST /api/projects/
GET  /api/tasks/
POST /api/tasks/{id}/comments/

These APIs are created in the Django backend using Django REST Framework.

The Angular frontend calls these APIs using HttpClient.

Simple example:

When user clicks Login in Angular:

Angular sends request to:

POST http://127.0.0.1:8000/api/auth/login/

Django backend checks email/password and returns user data plus JWT tokens.


2. WHAT IS API DOCUMENTATION?
=============================

API documentation is a guide/manual that explains how to use backend APIs.

It tells developers:

- What APIs exist
- What URL to call
- Which HTTP method to use
- What request body is required
- What response will come
- Which APIs need login token
- What query parameters are supported
- What errors can happen
- What data fields are required

Without API documentation, frontend developers must inspect backend code manually.

With API documentation, they can understand and test APIs from a browser.


3. WHY API DOCUMENTATION IS IMPORTANT
=====================================

In a real project, frontend and backend are often developed separately.

Backend developer creates APIs.
Frontend developer consumes APIs.

Frontend developer needs to know:

- Login API request format
- Employee create API fields
- Project response structure
- Task status options
- Whether JWT token is required
- How to pass Authorization header

API documentation solves this communication problem.

It acts like a contract between frontend and backend.


4. WHAT IS SWAGGER UI?
======================

Swagger UI is a browser-based interactive API documentation page.

In this project Swagger UI is available at:

http://127.0.0.1:8000/api/docs/

Swagger UI allows us to:

- See all backend APIs
- See API groups/modules
- See request method: GET, POST, PUT, PATCH, DELETE
- See request body format
- See response body format
- Test APIs directly from browser
- Authorize using JWT token
- Check backend responses immediately

Swagger UI is very useful during development and testing.

It works like Postman, but it is automatically generated from backend code.


5. WHAT IS OPENAPI?
===================

OpenAPI is a standard format for describing REST APIs.

It describes:

- API endpoints
- HTTP methods
- Request bodies
- Response bodies
- Authentication requirements
- Parameters
- Status codes
- Data schemas/models

OpenAPI is not mainly for humans.
It is mainly for tools and machines.

In this project, OpenAPI schema is available at:

http://127.0.0.1:8000/api/schema/

That URL returns a machine-readable schema.

Swagger UI reads this OpenAPI schema and displays it as a nice web page.


6. DIFFERENCE BETWEEN SWAGGER UI AND OPENAPI SCHEMA
===================================================

Swagger UI:

- Human-friendly
- Browser page
- Easy to read
- Easy to test APIs
- Used by developers manually

URL:

http://127.0.0.1:8000/api/docs/

OpenAPI Schema:

- Machine-readable
- JSON/YAML style API definition
- Used by Swagger UI and tools
- Can be used to generate API clients

URL:

http://127.0.0.1:8000/api/schema/

Simple relationship:

Django REST APIs
      ↓
drf-spectacular generates OpenAPI schema
      ↓
Swagger UI reads schema
      ↓
Developer sees API documentation in browser


7. WHAT PACKAGE DID WE USE FOR API DOCUMENTATION?
=================================================

This project uses:

drf-spectacular

9. WHAT IS HEALTH CHECK API?
============================

Health check API is a simple API that confirms whether backend is running properly.

In this project:

http://127.0.0.1:8000/api/health/

This API checks:

- Is backend server running?
- Is Django responding?
- Is database connected?

Example success response:

{
  "success": true,
  "message": "Health check completed successfully.",
  "data": {
    "service": "TaskVerse API",
    "status": "ok",
    "database": "connected"
  }
}

This means:

- Backend is alive
- API is reachable
- Database connection is working


10. WHY HEALTH CHECK IS USEFUL
==============================

Health check is useful for debugging.

Example problem:

Frontend says:

Registration failed. Please check that the backend server is running.

First thing to check:

http://127.0.0.1:8000/api/health/

If health check works:

Backend is running.
Problem may be API validation, token, CORS, or frontend issue.

If health check does not work:

Backend is not running or backend has an error.

Health check is also useful in production for monitoring tools.

14. HOW TO TEST PROTECTED APIs IN SWAGGER
=========================================

GET /api/departments/
GET /api/employees/
GET /api/projects/
GET /api/tasks/
GET /api/dashboard/summary/

To test protected APIs:

Step 3: Click Authorize button in Swagger UI.

Step 4: Enter token like this:

Step 6: Now call protected APIs.

- Request body

- Authentication requirement

So the relationship is:

Real API:

OpenAPI schema:
Machine-readable description of APIs.

Simple explanation:

API is the actual backend functionality.
API documentation is the manual for using that functionality.

33. HOW DRF-SPECTACULAR KNOWS ABOUT OUR APIs
============================================

drf-spectacular reads Django REST Framework configuration.

It looks at:

- URL patterns
- API views
- ViewSets
- serializers
- request fields
- response fields
- authentication classes

backend/config/urls.py

Serializers are also very important.

ProjectSerializer tells Swagger what project fields exist.

So Swagger documentation is generated from backend code.

35. HTTP STATUS CODES YOU WILL SEE IN SWAGGER
=============================================

APIs return HTTP status codes.

These codes tell whether the request succeeded or failed.

Common status codes in this project:

200 OK:
Request successful.
Example: GET /api/employees/ returns employee list.

201 CREATED:
New record created successfully.
Example: POST /api/departments/ creates department.

204 NO CONTENT:
Record deleted successfully or response has no body.
Example: DELETE /api/employees/{id}/

400 BAD REQUEST:
Validation error.
Example: Required field missing or duplicate email.

401 UNAUTHORIZED:
Authentication token missing or invalid.
Example: Calling protected API without Bearer token.

403 FORBIDDEN:
User is authenticated but does not have permission.

404 NOT FOUND:
Requested record does not exist.
Example: GET /api/employees/9999/

500 INTERNAL SERVER ERROR:
Backend server error.
This usually means there is a bug or unexpected exception.

Swagger helps us see these responses while testing.

37. HOW ANGULAR AUTOMATICALLY SENDS JWT TOKEN
=============================================

In this project, Angular has an auth interceptor.

File:

frontend/src/app/core/interceptors/auth.interceptor.ts

This interceptor checks every outgoing HTTP request.

If request URL starts with backend API base URL and access token exists, Angular adds this header automatically:

Authorization: Bearer <access_token>

That means protected APIs can work after login without manually adding token in every service.

Interceptor is registered in:

frontend/src/app/app.config.ts

It uses:

provideHttpClient(withInterceptors([authInterceptor]))

This is why after login, pages like Departments, Employees, Projects, Tasks can call protected APIs.

Swagger does not use Angular interceptor.

In Swagger, we manually click Authorize and paste token.

Angular does it automatically through interceptor.


38. WHY SWAGGER MAY NOT SHOW PERFECT REQUEST/RESPONSE IN SOME CASES
====================================================================

Swagger is generated automatically from backend code.

Most of the time it is accurate.

But sometimes Swagger may need extra hints if:

- API uses custom response wrapper
- API uses dynamic serializer
- API has custom actions
- API returns different response formats based on condition
- API uses complex nested data

In this project, we use a common response format like:

{
  "success": true,
  "message": "...",
  "data": {...}
}

Swagger can still document APIs, but for highly customized responses, backend developers sometimes add extra schema annotations.

47. WHAT HAPPENS IF TOKEN IS MISSING?
=====================================

If you call a protected API without token, backend rejects the request.

Example:

GET /api/employees/

If token is missing, response may be:

{
  "detail": "Authentication credentials were not provided."
}

Meaning:

You are trying to access a secured API without logging in or without sending JWT token.

Solution:

Login first, copy access token, and send it as:

Authorization: Bearer YOUR_ACCESS_TOKEN


48. WHAT ARE HTTP METHODS?
==========================

HTTP methods tell the backend what action we want to perform.

Common HTTP methods used in this project:

GET:
Used to read/fetch data.

Example:
GET /api/employees/

POST:
Used to create new data or perform an action.

Example:
POST /api/employees/

PUT:
Used to update the full record.

Example:
PUT /api/employees/1/

PATCH:
Used to update only selected fields.

Example:
PATCH /api/employees/1/

DELETE:
Used to delete a record.

Example:
DELETE /api/employees/1/

50. WHY THIS IS IMPORTANT IN REAL PROJECTS
==========================================

In real companies, backend and frontend teams may work separately.

Backend developer creates APIs.

Frontend developer uses those APIs.

API documentation helps frontend developers understand:

- Which API URL to call
- Which HTTP method to use
- What request body is needed
- What response body will come
- Which APIs require authentication
- What errors can happen
- How to pass JWT token

Without API documentation, frontend developers must ask backend developers again and again or read backend code manually.

Swagger/OpenAPI avoids confusion.

It works like a clear contract between backend and frontend.
